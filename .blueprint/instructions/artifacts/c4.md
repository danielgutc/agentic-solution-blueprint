# C4 Artifacts

## Purpose

Represent approved architecture at the smallest C4 level needed by the audience.

## Canonical shapes

Use the corresponding files under `.blueprint/templates/c4/`.

## Levels

- System: scope, actors, external systems, responsibilities, and boundaries.
- System containers: authoritative runtime and data boundaries plus their interactions.
- Container: one runtime or data-store boundary as a black box.
- Component: cohesive responsibilities, architectural interfaces, dependencies, constraints, invariants, and rationale inside an approved container.
- Code projection: canonical unit/profile API pages plus generated container, optional component, and architectural-interface link views derived from implementation source, API comments, tests, and approved C4 bindings.

## Authoring rules

- Model one abstraction level per view.
- Define scope and boundary before adding elements.
- Use stable identifiers and domain vocabulary.
- Describe responsibilities and directional relationships, not only technologies.
- Keep data ownership and runtime authority explicit.
- Do not equate bounded contexts, repositories, deployment units, and microservices without an explicit decision.
- Do not derive C4 identifiers or diagram structure from source paths. Record C4-to-implementation-unit mappings in `design/foundation/tech.md` and traceability artifacts according to `../standards/implementation-layout.md`.
- Do not create an implementation directory for a managed service, stock image, or data-store container unless the repository owns source, configuration, validation, or packaging for it.
- Use microservices only when independent ownership, deployability, scaling, release cadence, or failure isolation justifies their distributed-system cost.
- Record merge, split, replacement, and migration triggers so the architecture can evolve without speculative decomposition.
- Use `../standards/design-by-contract.md` for container and component boundaries.
- Split diagrams by concern rather than making one unreadable view.
- Follow `../standards/navigation.md` for breadcrumbs, contents lists, contained-element links, and C4 drill-down.
- Use `.drawio` source with a committed sibling `.svg` export for each referenced human-authored diagram, following `../standards/diagram-tooling.md`. Record an approved exception in `design/foundation/tech.md` before using another source format.
- Include a system-context diagram for system review and a container-landscape diagram for system-containers review. Do not mark the C4 view approved while its required diagram source, export, or navigation links are missing; record any scoped exception with rationale and owner.
- Keep components nested under their owning container.
- Add component decomposition only during technical design.
- Keep enduring technical documents beside their primary architectural owner. Use `design/c4/containers/<container>/<document>.md` for container-owned or same-container cross-component material and `design/c4/containers/<container>/components/<component>/<document>.md` for component-owned material. Walking skeletons, focused assessments, recovery notes, contract designs, and test designs follow this same rule.
- Determine placement by primary scope and decision ownership, not by filename or incidental references. Technical documents with shared ownership across containers and no single container owner declare their scope at the participants' common C4 level and are linked from each participant rather than duplicated under one container or component.
- Link owned documents from `container.md` or `component.md` only after they exist. Record lifecycle status, requirement coverage, coordination, and readiness evidence by linking from the relevant foundation artifacts rather than duplicating the technical content there.
- Keep source interfaces, API comments, executable tests, implementation-local documentation, generated code projections, and API reports in their registered source or output locations; do not relocate them merely because they concern a container or component.
- For each repository-owned implemented container/profile binding, link `container.md` to its generated `code.md`. Link an implemented `component.md` to its generated `code.md` only when that optional filtered component view exists. A container with no approved component decomposition still receives its configured container entry view; do not create placeholder views before implementation exists.
- Keep exact generated symbol content canonical under `design/code/<implementation-unit>/<documentation-profile>/api/`. Container `code.md`, optional component `code.md`, and `_code-views/interfaces.md` link to canonical pages rather than copying signatures.
- Keep component architecture human-authored: responsibilities and provided/required ports belong in `component.md`, not an inventory of implementation types. Keep external runtime contracts in `container.md`, and distinguish contained components from internal architectural interfaces.
- Never edit generated canonical pages, C4 code views, compatibility stubs, or generated code-diagram sources manually.

## Quality checks

- Narrative and diagrams agree.
- Every referenced diagram has a current source/export pair and working Markdown and visual links.
- Boundaries trace to approved design decisions.
- Provider and consumer obligations are visible.
- Each owned technical document is placed at the smallest approved C4 scope that owns its decisions and traces to the relevant contracts, test seams, and readiness evidence.
- Persistence ownership is unambiguous.
- Lower-level detail does not leak into higher-level views.
- Generated projections can be reproduced from a clean checkout.
- Generated canonical pages and C4 code views identify implementation unit, documentation profile, included and excluded source/language/visibility scope, generator version, parser limits, provenance, reproduction command, and every configured architecture binding; their source/API/navigation links resolve.
